QUE CONTIENE ESTE ARCHIVO
-------------------------------------------------------------------------------
SOLO identificadores publicos o de bajo riesgo: App ID, Business ID, page_id,
act_..., WABA ID, Phone Number ID. Son numeros que identifican cosas y no dan
acceso a nada por si solos.

NINGUN secreto. Estos cinco NO estan aqui y no deben estarlo nunca:
    META_APP_SECRET, META_WEBHOOK_VERIFY_TOKEN, META_PAGE_ACCESS_TOKEN,
    WHATSAPP_ACCESS_TOKEN, META_MARKETING_ACCESS_TOKEN
Un "token" NO es un identificador: es una llave. Viven solo en el `.env` del
servidor, que esta en .gitignore. Este archivo SI se versiona.

La clave secreta de la app estaba visible tras un boton "Mostrar" en el panel.
NO se pulso, a proposito.

0. HALLAZGO PRINCIPAL — LEE ESTO ANTES QUE LOS NUMEROS
===============================================================================

Los activos de MotoMas NO estan en un solo porfolio empresarial. Estan
repartidos en CINCO:

  PORFOLIO                              ACTIVOS   BUSINESS ID
  ------------------------------------- --------  -------------------
  Motomas S.A Sucursales                7         1398827153319161
  GM MOTOS Taller Y Repuestos: Central   8         (no consultado)
  Motomas Nicaragua Sucursales           0         1414077217221690
  Motomas Las Mercedes                   1         (no consultado)
  Motomas Multicentro                    0         (no consultado)

Esto choca de frente con una decision de diseno del repositorio, documentada en
docs/META_INTEGRATIONS.md §8.1 y en el comentario del modelo `MetaAdAccount`:

    "Todas las cuentas cuelgan del mismo Business Manager y son del mismo
     negocio, asi que UN token basta para leerlas todas: no hace falta un OAuth
     por cuenta."

Con cinco porfolios, esa premisa es FALSA. Consecuencias reales:

  1. Un Usuario del Sistema pertenece a UN porfolio. Su token solo alcanza los
     activos de ESE porfolio. Para leer las cuentas publicitarias de GM MOTOS y
     de Las Mercedes harian falta tokens distintos.
  2. `META_MARKETING_ACCESS_TOKEN` es UNA sola variable de entorno. El codigo no
     contempla un token por porfolio.
  3. Lo mismo para las paginas: `META_PAGE_ACCESS_TOKEN` es una sola variable.

  QUE HACER (decision de negocio, no tecnica — hay que tomarla antes de seguir):
    Opcion A — Consolidar: mover todos los activos al porfolio "Motomas S.A
               Sucursales". Es lo que el codigo espera hoy y no requiere tocar
               nada. Mover activos entre porfolios en Meta es lento y a veces
               requiere soporte.
    Opcion B — Empezar solo con "Motomas S.A Sucursales" (7 activos) y dejar los
               otros porfolios fuera del CRM por ahora.
    Opcion C — Cambiar el codigo para soportar varios tokens. Es trabajo real:
               nueva tabla, nueva UI, y `META_MARKETING_ACCESS_TOKEN` deja de
               ser una variable de entorno.

  RECOMENDACION: Opcion B para arrancar, y A o C despues, con calma.

Segundo hallazgo, menor pero relevante: el porfolio "Motomas Nicaragua
Sucursales" (1414077217221690) esta RESTRINGIDO — Meta dice literalmente "No
puedes usar este porfolio empresarial para publicar anuncios". Tiene 0 activos.
No sirve para nada de esto.

  PERMISO                 ESTADO EN META      LO USA EL CRM?
  ----------------------  ------------------  --------------------------------
  ads_read                Listo para prueba   SI (meta-ads/client.ts)
  ads_management          Listo para prueba   NO — y no deberia estar
  business_management     Listo para prueba   NO
  pages_show_list         Listo para prueba   SI (para conocer los page_id)
  pages_read_engagement   Listo para prueba   NO
  public_profile          Listo para prueba   —
  Marketing API Access Tier  Acceso limitado  (limita frecuencia de peticiones)

  "Listo para prueba" = solo funciona con activos donde tu usuario es
  administrador. No ha pasado App Review.

  AVISO DE SEGURIDAD: `ads_management` esta activado en el caso de uso. Es el
  permiso que permite crear campanas, pausarlas y mover presupuestos — o sea,
  GASTAR DINERO. El repositorio decidio explicitamente no pedirlo todavia
  (docs/META_INTEGRATIONS.md §8.1: "NO le des ads_management ... Se pedira mas
  adelante, junto con topes de gasto duros, y no antes de que esos topes
  existan").
  El codigo de hoy solo hace peticiones GET, asi que el riesgo no viene del CRM
  sino del token: si generas el token del Usuario del Sistema y le marcas
  ads_management, tendras en el `.env` una llave capaz de gastar sin ningun tope
  que la limite. Al generarlo, marca UNICAMENTE `ads_read`.

--- 9.2 Lead Ads: NO EXISTE ---

  La app tiene DOS casos de uso: "Crea y administra tus anuncios" y "Conecta con
  los clientes a traves de WhatsApp". NO hay ningun caso de uso de clientes
  potenciales.

  Por tanto FALTAN los dos permisos imprescindibles de Meta-1:

      leads_retrieval        <- sin este, el CRM no puede leer las respuestas
                                del formulario. Los leads llegarian vacios.
      pages_manage_metadata  <- sin este, no se puede suscribir la pagina al
                                webhook.

  Hay que anadir el caso de uso correspondiente en "Casos de uso -> Anadir casos
  de uso" antes de que Lead Ads pueda funcionar.

9.5 ESTADO VERIFICADO DE LAS CREDENCIALES (2026-09-01, contra la Graph API)
===============================================================================
Comprobado con /debug_token. No se imprimio ningun valor en ningun momento.

META_APP_SECRET .......... CORRECTA Y VALIDA.
    La propia llamada a /debug_token se autentico con `APP_ID|APP_SECRET` y
    Meta respondio con datos en vez de un error de OAuth. Eso demuestra que el
    secreto de aplicacion configurado es el bueno.

META_WEBHOOK_VERIFY_TOKEN  NO VERIFICABLE DESDE FUERA.
    Es una cadena que elige uno mismo; Meta no la valida hasta que se suscribe
    el webhook. Esta puesta en el .env local. Si el valor de produccion es otro,
    la suscripcion fallara.

META_PAGE_ACCESS_TOKEN ... INSERVIBLE. Tres defectos, cada uno bloqueante:
    1. CADUCADO. Expiro el 2026-09-01 a las 18:00 UTC. Es un token de corta
       duracion del Graph API Explorer.
    2. TIPO EQUIVOCADO. Es un token de USUARIO (`type: USER`), no de PAGINA.
       `fetchLeadgenDetail` en src/server/meta/ingest.ts lee el nodo del lead y
       eso exige un token de PAGINA.
    3. ALCANCES INSUFICIENTES. Solo trae `business_management` y
       `public_profile`. NO trae `leads_retrieval`, que es el imprescindible.

    Conclusion: aunque no hubiera caducado, jamas habria podido traer un lead.
    Hay que generar uno nuevo, de PAGINA y de larga duracion, DESPUES de que
    `leads_retrieval` quedara activo (se activo el 2026-09-01): un token emitido
    antes no lleva ese alcance aunque el permiso exista ahora.
